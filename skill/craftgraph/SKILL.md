# 用 CraftGraph 回答「怎么做」与「产线怎么建」

CraftGraph 把**正在运行的游戏**里的配方数据通过 MCP 暴露出来。它的输出是**事实**，
你的工作是**引用它、解释它、把缺口说清楚** —— 不是重新算一遍。

## 先记住这一条

> 工具给了表和数字，就引用它。工具说「未知」，你就说未知。
> **不要手工重算速率或台数，也不要替工具补它没给出的数字** ——
> 报告里「未知」后面都跟着原因（多半是读不到耗时），把原因一起转达就够说明问题了。

这条是这份 skill 存在的主要理由：手工推导出来的数字看起来更丰富，但它没有出处，
读者无法核对；而且一旦工具下次给出正确的表，你的推导就成了矛盾的第二份答案。

## 三种提问，三条流程

### 1）「X 怎么做」→ `build_recipe_tree`

不需要产量。调一次，把「展开过程」和「基础原料汇总」转达出来即可。

### 2）「X 有什么用」→ `get_recipes_for_input`

再按需 `get_recipe_details` 看具体配方。

### 3）「帮我设计 X 的产线」→ `calculate_production_plan`

**第一步永远是确认产量**：`ratePerMinute` 是必填的，而「随便定一个」会让整份规划失去意义
（实测：模型自己挑了 8/分，最后又回头问「告诉我你实际想要多少」）。

- 用户给了产量 → 直接算。
- 用户没给 → **先问**：「每分钟要多少 X？」并说明为什么问（机器台数、原料速率都按它缩放）。
- 用户说「我还没想好，先看看需要什么」→ 用 `build_recipe_tree`（不需要产量），
  或者明确提出「那我先按 1 个/分算，你要的是相对比例而非绝对产量」。

拿到规划后，**照抄它的段落结构**，见下面的「回答模板」。

## 输出的图例与两个容易混的参数

| 记号 / 字段 | 含义 |
|---|---|
| `●` | 没有配方能产出它 → 基础原料（到此为止） |
| `↳ 配方（类型）执行 N 次，每次产出 M` | 这一步用什么、要做几次 |
| `✂ 达到深度上限，未展开` | **没算**这个分支 → 原料表不完整 |
| `⋯ 该分支未展开，共 N 节点 / M 条配方；原料 …` | **算了但没展开显示** → 数字仍然完整 |
| `opaque` / 「读不懂」 | 有配方但输入输出读不出来。**不等于不需要材料** |
| 「不产出物品」 | 读了它的产出字段，确实没有产出（如燃料定义）——与「读不懂」是两回事 |
| 概率产出 | 产量是**期望值**，不是保证值 |

**两个深度参数作用完全不同**（用户问「深度是什么意思」时就讲这个）：

- `maxDepth`（**计算**用，默认 8，范围 1–32）：超过就不算了 → 该分支的原料**没被计入**，
  报告顶部会出现「这份配方树不完整…不要直接拿去建产线」的警告。看到 `✂` 才说明答案真的缺东西。
- `detailDepth`（**显示**用，默认 2，范围 0–64）：只影响打印多少行，被折叠的分支会带一行规模摘要，
  **汇总数字仍然是全树的**。看到 `⋯` 只是显示被压缩了，答案没变。

处理方式：看到 `✂` → 调大 `maxDepth`，或**直接把被截断的那个物品再问一次**（更省）；
看到 `⋯` → 调大 `detailDepth`，或对那个物品单独问一次。

## 回答模板

用户抱怨最多的是「读起来像模型在自证推理」。按这四段组织：

1. **结论** —— 选哪条配方、一句话为什么（产出倍数、原料是否是标签、耗时是否已知）。
2. **环节表** —— 直接引用报告里的「需要多少机器」（每个环节一行：机器 / 耗时 / 台数，
   **算不出的会写成「未知」**）、「每分钟原料需求」、「副产物」（有可回代的会在那里提示）。
   **工具写「未知」就照写「未知」**，不要留空、不要自己填一个下限上去。
3. **缺口** —— 工具已经在报告开头给出「这份规划缺什么（先看这里）」，**照它转达即可**，
   不要自己再汇总一遍（那正是它存在的原因）。它按类列：台数算不出 / 原料链到此为止 /
   有环节没展开 / 按期望值估算 / 数据底子，末尾还有一句结论（能不能照着建）。
4. **可选优化** —— 只在工具给出提示时提（例如某副产正好是另一环节的输入）。
   没提示就不要凭空发明「更优解」。

## 必须如实转达的五件事

1. **标签选择**：`#forge:ingots/iron` 意味着「任意一种铁锭都行」，工具已经挑了一个，
   要说明挑了哪个；用户在意的用 `tagChoice` 覆盖。
2. **opaque**：「读不到」就是读不到，不要说成「不需要材料」。
3. **概率产出**：是期望值。
4. **截断 / 循环**：必须说，并说明这让数字偏低。
5. **耗时未知**：说明它导致台数算不出。常见原因见下节。

## 常见现象的归因（别把包的锅说成工具的锅）

| 现象 | 通常的原因 |
|---|---|
| 某类配方**读不到耗时** | KubeJS 写的配方常常没写 `processingTime`，Create 把它当 0；工具按「未知」处理（报 0 会算出无穷台机器）。实测一个包：`create:sequenced_assembly` 只有 22/227 有耗时 |
| 配方有耗时但**没有机器名** | Create 不覆写 `getToastSymbol()`，工具刻意不采信默认值（那会把所有模组机器都标成工作台）。这是已知缺口，等 JEI/EMI 催化剂 |
| 整包**读不懂比例高** | 该包的模组用了自定义配方格式、还没适配器 → `npm run inspect` 能列出来（这是可以补的） |
| 说「这物品没有配方」 | 先确认不是 opaque：`get_recipe_details` 看 `opaque` 字段，别把「读不懂」说成「没有」 |

## 工具速查

| 用途 | 工具 |
|---|---|
| 状态 / 覆盖度 / 离线与否 | `get_bridge_status`，重载用 `refresh_recipes` |
| 找物品 id（用户说「铁锭」「钢」这类俗称） | `search_items` |
| 查产出 / 查用途 / 看详情 | `get_recipes_for_output` / `get_recipes_for_input` / `get_recipe_details` |
| 某物品还有哪些配方 | `find_alternative_recipes` |
| 配方树（不需要产量） | `build_recipe_tree` |
| 产线规划（**需要产量**） | `calculate_production_plan` |
| 标签成员 / 类型统计 / 注册表 | `expand_tag` / `list_recipe_types` / `get_registry` |

对结果不满意时用参数覆盖，而不是重新描述一遍问题：
`recipeChoice`（指定某物品用哪条配方）、`tagChoice`（指定标签选哪个成员）、
`rawMaterials`（声明某物品是基础原料，不再往下展开）。

## 反模式（都来自一次真实会话的失败）

- ❌ 手工算「每个产物吃 500 mB → 4 次/分 → 2000 mB/min」这一串 —— 该由 `calculate_production_plan` 给。
- ❌ 从「逐环节明细」里凑出一句「1 台/环节」当机器数 —— 机器表已经明确写了「未知」，
  照它说就行；那是下限，不是可用数字。
- ❌ 自己挑一个产量（「8/分 是我随便定的」）然后整篇按它推导。
- ❌ 把截断分支的结果当完整原料表用。
- ❌ 在没查 `get_recipe_details` 之前断言「这个包里没有它的配方」。
