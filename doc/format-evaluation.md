# 紧凑格式评估（对 doc/raw-form.md 的实测回应）

结论先说：**raw-form.md 的优先级判断方向正确，但「字典编码」这一项在本项目的使用场景下不成立。**
实测发现，字典的收益在**必须随每次工具调用重发**时会完全蒸发；而「列式」这一项是真实有效的。

测量工具：`npm run compare`（`mcp-server/src/format-compare.ts`），
数据规模 1 万条配方，同一份树的同等信息量做对比。
token 数用 `gpt-tokenizer` 实际计数，不是估算。

---

## 1. 实测结果

### 配方树（408 节点）

| 格式 | tokens | 相对 markdown |
|---|---:|---:|
| markdown（当前默认） | 21,291 | +0% |
| 紧凑 JSON | 36,770 | +73% |
| **列式 TSV，无字典** | **15,396** | **-28%** |
| 列式 TSV + 字典，仅数据行 | 9,814 | -54% |
| 列式 TSV + 字典，数据行与字典一起发 | 15,460 | **-27%** |

### 配方列表（120 条候选配方）

| 格式 | tokens | 相对 markdown |
|---|---:|---:|
| markdown（当前默认） | 4,065 | +0% |
| 紧凑 JSON | 5,361 | +32% |
| 列式 TSV，无字典 | 3,810 | -6% |
| 列式 TSV + 字典，仅数据行 | 1,573 | -61% |
| 列式 TSV + 字典，数据行与字典一起发 | 3,458 | **-15%** |

### 产线规划

| 格式 | tokens | 相对 markdown |
|---|---:|---:|
| markdown（当前默认） | 27,755 | +0% |
| 紧凑 JSON | 50,914 | +83% |

## 2. 关键发现：字典的收益是假的

对比这两行：

```
列式 TSV，无字典                          15,396
列式 TSV + 字典，数据行与字典一起发          15,460   ← 比不用字典还贵 0.4%
```

**加了字典之后，总开销和不加字典完全一样。** 字典省下的部分，恰好等于字典本身的成本。

原因很直接：字典要 5,646 tokens，而它省下的是 15,396 - 9,814 = 5,582 tokens。两者抵消。

配方列表上更明显：字典 1,885 tokens，只省下 3,810 - 1,573 = 2,237 tokens，净赚 352（-15%）。

### 那 -54% 和 -61% 是怎么来的？

那两行假设**字典已经在上下文里存在**。raw-form.md 第 6 节写的「缓存字典：同一会话中字典只发一次」
就是这个假设。问题是这个假设在 MCP 上不成立：

1. **MCP 的工具结果相互独立。** 服务端发一次字典，无法保证客户端在后续调用时还留着它。
2. **上下文压缩会丢掉早期结果。** 长会话里前面的字典行被裁掉后，模型看到 `i0:1` 却查不到 `i0` 是什么。
3. **服务端不知道客户端留了什么。** 没有可靠的确认机制，所以只能假设最坏情况。

**这不是实现问题，是协议层面的性质。** 所以「字典只发一次」不能作为设计前提。

### 字典什么时候才划算

字典的收益正比于**值的重复率**。配方数据恰好是最不利的情况：
配方 id、物品 id 在一条列表里几乎都是唯一的，重复率很低。

安全可用的字典只有一种：**无状态的自包含字典**（把字典和数据一起发）。
但那时它就不省了 —— 见上面的 15,460 vs 15,396。

---

## 3. 值得采纳的部分：列式

**列式 TSV 无字典在配方树上省 28%，而且没有任何状态依赖。** 这部分是纯赚的。

为什么树省得多、列表只省 6%：markdown 的结构开销是随**嵌套深度**增长的。

- 树的每个节点要付 `2 空格 × 深度` 的缩进 + `- ` 项目符号 + `**粗体**` + `_斜体_`。
  深度 6 的节点光缩进就 12 个字符，400 个节点累计下来很可观。
- 列表每条只有一行，本来就没有嵌套，markdown 的开销只剩下 `- ` 和反引号，所以压缩空间小。

**推论：列式对该项目的价值随嵌套深度增长。** 深加工链（科技整合包的主要场景）正是它最值钱的地方。

### 顺带纠正 raw-form.md 的一条原则

> 原则 1：**Schema 外置**：列名、字段含义写在 MCP 工具描述里，数据只返回值。

实测下来这条**不建议照做**。上面那些 TSV 数字里**都带了一行列名头**（`depth|parent|count|...`），
这一行的成本约 30 tokens，换来的是数据自描述。

而把 schema 外置到工具描述会带来两个问题：

1. 工具描述是**每次会话固定发送**的（当前 12 个工具的定义共 2,261 tokens）。多几个 DSL 工具、
   每个多一段格式说明，这笔固定开销会持续增长。
2. 模型要跨「工具描述」和「工具结果」两处做脑内 join。少一次关联就少一类出错可能。

30 tokens 换掉一整个错误类别，这笔买卖划算。**表头留在数据里。**

---

## 4. 建议

| 项目 | 建议 | 理由 |
|---|---|---|
| 紧凑 JSON（去掉缩进） | ✅ **已实施** | 省 28%，零风险 |
| 标签候选/替代配方只报数量 | ✅ **已实施** | 树省 30%，信息可用 `expand_tag` 按需取 |
| 重复说明挪到开头图例 | ✅ **已实施** | 树再省约 13 个百分点 |
| 列式 TSV（无字典） | ✅ **已实施为 `format: "tsv"`** | 实测省 17~26%，无状态依赖。markdown 仍是默认，便于后续 A/B |
| 配方树分层返回 | ✅ **已实施为 `detailDepth`** | 收益远大于格式优化，见 §6 |
| **字典编码** | ❌ **仍不建议** | 实测净收益 ~0%，且依赖不可靠的跨调用状态 |
| MessagePack / CBOR / gzip | ❌ **不建议** | raw-form.md 自己的判断正确：对模型上下文无益 |

## 5. 实施后的复测（重要修正）

上面 §1 的表格是**优化前**的对比。①②③ 和分层返回都实施后重新测了一遍，
有一处结论需要修正：

| 格式 | 完全展开 | 分层默认（detailDepth=2） |
|---|---:|---:|
| markdown | 15,585 | 1,855 |
| 列式 TSV | 12,926 | 1,372 |
| **TSV 相对 markdown 的优势** | **-17%** | **-26%** |

**列式的边际收益从 -28% 降到了 -17%。** 原因是 markdown 自己也变紧凑了 ——
列式原本的一部分优势来自「去掉了 markdown 的冗余结构」，而那些冗余我在 ①②③ 里已经从
markdown 侧清掉了。两者不是叠加关系，而是部分重叠。

这不改变「列式值得做」的结论，但说明**优化项的收益要一起测，不能逐项相加**。
另外要注意工具定义的固定开销从 2,261 涨到 2,598 tokens（新增参数的说明文字），
单个会话调用次数多时才摊得平。

### 分层返回（`detailDepth`）的实测收益

这是本轮最大的单项收益，远超任何格式改动：

| 项目 | 完全展开 | 分层默认 | 变化 |
|---|---:|---:|---:|
| 配方树 markdown（318 节点） | 15,585 | **1,855** | **-88%** |
| 产线规划 markdown | 20,304 | **6,832** | -66% |
| 典型会话 | 16,861 | **3,131** | -81% |
| 最坏会话 | 37,350 | **10,148** | -73% |

关键设计：**裁剪只影响「展示多少结构」，基础原料仍是全树算出来的。**
未展开的分支挂上 `subtree` 统计（节点数、配方数、该分支的原料合计），
所以 agent 不展开也能知道那个分支有多大、需要什么。这条性质在 `smoke.ts` 里有专门断言 ——
一旦坏掉，agent 会拿到偏低且看不出问题的原料表，比「太贵」严重得多。

一个实施中发现的细节：那行全局说明（「结构只展示到第 N 层…」）约 150 字符，
而折叠一个节点通常只省 20 tokens。所以小规模树上加说明反而更长（实测 4 节点的树
加了说明从 627 变 688 字符）。现在改成只在隐藏节点数 ≥ 8 时才加 ——
每个折叠节点上的 `⋯` 已经自带说明，全局那行是冗余的。


### 为什么列式做成了选项而不是默认

列式省 17~26% 是真的，但它**换掉了模型熟悉的 markdown 结构**。markdown 的缩进和项目符号
在预训练语料里出现极其频繁，模型对它的解析几乎是零成本；TSV 需要模型把注意力对准列位置关系。

省下的 token 是确定的，解析准确率的损失我无法自动测量。所以做成了 `format: "tsv"` 选项，
**markdown 仍是默认**。后续在实际使用中 A/B：同一批问题用两种格式分别问，
看 agent 需要几轮才给出正确答案。如果 TSV 没有增加往返轮数，再改默认值。

## 6. 比格式更值钱的：减少返回量

raw-form.md 第 6 节最后一条说对了，而且它比前面所有格式优化加起来更重要：

> **分页/按需查询**：再省也不如只返回 AI 真正需要的那部分。**

实测支持这个判断：

| 场景 | tokens |
|---|---:|
| 列表默认 30 条（当前默认值） | 1,069 |
| 同样列表放开到 120 条 | 4,065 |

**只是把分页默认值从 30 调到 120，成本就是 4 倍。** 格式再怎么压也追不回这个量级。

同样地，配方树的成本几乎全部来自「一次把整棵深树倒出来」。所以真正的杠杆是**分层返回**，
这一项已经实施（见 §5）：默认只展示三层结构，未展开的分支挂上规模和原料摘要。

结果印证了判断：分层返回带来 **-88%**，而列式格式只带来 **-17~26%**。
「少返回」确实比「压得更紧」值钱得多。

顺带一个衍生结论：`get_recipes_for_output` 的分页默认值是 30，这个值目前是拍的。
等实际用起来应该按候选数分布重新定 —— 但要先有真实数据，现在调只是换一个猜法。
